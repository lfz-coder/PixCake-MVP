# 预览滑杆延迟优化证据

日期：2026-11-09  
范围：4000×3000 RGBA8 预览、CPU reference fallback、全局/局部调色滑杆
来源边界：[PhotoCraft 能力来源与 PixCake 移植规范](../specs/2026-11-09-photocraft-reference-and-porting-policy.md)。本文测的是当前 PixCake reference 的执行优化；移植 PhotoCraft 公式时必须保持同一执行路径和新的 parity 证据，不能把这里的旧公式视为最终行为。

## 基线与复测

使用仓库已有的 `bench_reference_render`，在同一台机器、同一构建配置下运行。该基准选择 reference 路径，因为当前命令行会话无法创建 native OpenGL context；GPU 路径没有被这次改动替换。

| 滑杆/绘制组 | 优化前 | 优化后 | 减少 | 优化幅度 |
| --- | ---: | ---: | ---: | ---: |
| 曝光（单通道影调） | 316.2 ms | 17.8 ms | 298.4 ms | 94.4% |
| 色阶（RGB 复合） | 364.5 ms | 11.0 ms | 353.5 ms | 97.0% |
| HSL | 605.6 ms | 409.5 ms | 196.1 ms | 32.4% |
| 黑白 | 579.4 ms | 356.3 ms | 223.1 ms | 38.5% |
| 选择性颜色 | 581.7 ms | 303.5 ms | 278.2 ms | 47.8% |
| 颜色分级 | 433.1 ms | 245.2 ms | 187.9 ms | 43.4% |
| 全部颜色组 | 951.9 ms | 836.0 ms | 115.9 ms | 12.2% |
| 颗粒 | 485.3 ms | 468.3 ms | 17.0 ms | 3.5% |
| 局部蒙版 | 331.0 ms | 294.5 ms | 36.5 ms | 11.0% |
| 局部蒙版 + 屏幕图层 | 656.5 ms | 566.4 ms | 90.1 ms | 13.7% |
| 24 MP 全部颜色组 | 1951.0 ms | 1678.7 ms | 272.3 ms | 14.0% |
| 拖动预览（600 px，全颜色组） | — | 22.6 ms | — | — |

在同一“全部颜色组”场景里，旧链路拖动时按 4000 px 绘制约 951.9 ms；新链路拖动按 600 px 的 renderd 绘制约 22.6 ms，绘制耗时约减少 97.6%。这部分收益来自交互预览边长和请求/显示合并，公式没有改写。

命令：

```text
cmake --build build --target bench_reference_render -j2
build/tests/bench_reference_render
```

数字是该基准每个案例三次运行中的最短帧时间，代表“renderd 完成像素绘制”的延迟，不包含窗口事件分发和跨进程共享内存复制。实际机器若启用 native GPU，绝对值会不同，但 GPU shader 路径不受这次 CPU 快速路径改变。

## 实现

- `gpu/render/src/render_executor.cpp` 对只包含曝光、亮度、对比度和正向色温的通道独立影调建立 256 项 byte LUT；同一 LUT 也覆盖 RGB 复合色阶，再按原 reference 的顺序执行、最后使用相同的 clamp 和 `lround`。
- **2026-11-09 接入 PhotoCraft 公式后**：快速路径只保留曝光、亮度和 RGB 复合色阶（Camera Raw 曝光增益、现代亮度曲线和色阶都逐通道独立）；对比度改为作用于亮度的 Camera Raw S 曲线，不再逐通道独立，因此退出快速路径；色温/色调的线性光增益虽然逐通道独立，当前仍走通用路径（以后可以加入快速路径）。表由通用路径的同一组函数在灰阶上生成，逐字节相同。
- HSL/黑白直接计算相邻色相带，选择性颜色只遍历实际启用的目标，颗粒复用每个像素的晶格坐标，单蒙版和不透明普通混合走专门分支；这些都是执行层优化，原公式和执行顺序没有改动。
- 只有需要跨通道处理的负向色温、色调、复杂蒙版和图层仍走通用路径，但也受益于最新帧合并和专门的蒙版分支。
- `apps/shell/shell_controller.cpp` 在一次 socket 可读事件中先排空帧，只复制最新帧的 QImage；直方图则由 `HistogramRefreshGate` 只接受高清帧，拖动中的过期帧不再触发整张图的统计和 UI 工作。
- `PreviewSession` 拖动请求使用 600 px 交互帧，松开滑杆的 commit 请求恢复 `max_edge`（默认 4000 px）；交互帧只负责即时反馈，最终结果仍由高质量帧确认。
- 精修画布底部状态栏的 `2000px/3000px/4000px 预览` 入口通过 QMenu 修改 `PreviewSession` 的预览上限；菜单切换立即按当前档位重画。导出会继续读取原图并走独立的导出尺寸链路，因此这个设置不改变导出分辨率或水印策略。
- renderd 在一次读取循环中继续只保留最新的滑杆请求；服务端的单槽 `pending_` 也会覆盖旧请求，避免快速拖动时把过期帧排队算完。600px 全色彩组基准约 22.6 ms/帧（约 44 fps），因此旧帧不会把当前滑杆值拖到后面。
- 直方图复用同一批预览帧：拖动阶段由 `HistogramRefreshGate` 拒绝 600px 交互帧的采样，`PreviewView` 保留上一张高清快照并只显示“调节中，直方图暂未更新”提示；提交请求对应的高清帧到达后才计算并刷新 RGB 直方图。首帧、预览档位切换和一次性提交直接等待高清帧，不改变原有直方图算法。
- 画布把高清帧尺寸记录为稳定的逻辑画布尺寸；拖动时仍可使用 600px 实际帧，但按同一逻辑矩形放大显示，fit/zoom/画笔光标不会因为低清帧到达而跳变。GPU texture 仍由 renderd/backend 管理，界面没有另起一条采样管线。
- 第二阶段显示优化遵守桌面壳层约束：`PixCakeImageView` 继续是普通 Qt 控件，不在窗口控件里创建 OpenGL context 或提交 shader；每张到达的预览帧只转换一次并缓存为 `QPixmap`，paintEvent 直接复用缓存按稳定逻辑矩形绘制，避免每次重绘重新做 QImage 缩放。这样变化的是预览帧的清晰度，画布的显示尺寸、缩放比例和导出尺寸不变。

## 正确性检查

`tests/gpu/test_reference_color_groups.cpp` 新增了快速路径与强制走通用路径的逐字节比较，覆盖影调、色阶和正向色温；最终选定的 11 项 renderer/preview 测试全部通过。2026-11-09 接入 PhotoCraft 公式后，该测试改为覆盖亮度单独、曝光+亮度+色阶组合，不透明与半透明图各一次。

## 2026-11-09 接入 PhotoCraft 公式后的复测

上面的数字测的是旧公式。接入后在负载较高的同一台机器上交替运行改动前（`095e3fe`）与改动后各两次：曝光快速路径 123–135 → 151–199 ms，全部颜色组 812–920 → 1508–1556 ms，600 px 拖动预览 24–31 → 42–45 ms（约 23 fps）；GPU 列约 650 ms 不变。慢下来的主要是 CPU reference 的 Camera Raw Color Mixer。完整表和说明见[逐像素移植证据](2026-11-09-camera-raw-per-pixel-port.md)“性能”。
