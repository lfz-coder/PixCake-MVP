# PixCake 第三方依赖优先与引入规范

日期：2026-11-06  
状态：全局约束  
适用范围：仓库内所有生产模块、进程、平台适配器和构建目标。

## 1. 总原则

实现通用能力时，优先评估成熟、维护中的第三方库。已经有合适库覆盖的能力，不得为了“自己可控”而手写生产实现。图像解码、图像编码、缩放、色彩管理、标准格式解析、密码学、压缩、模型运行时和通用 IPC 编解码都属于这一原则覆盖的能力。

本项目自己实现的部分应限于项目语义和适配层：参数/文档契约、结果码、尺寸和长度校验、任务生命周期、队列事务、资源释放，以及把第三方库转换为项目已有的数据结构。适配层不能把第三方库的错误伪装成成功，也不能用占位像素或假文件掩盖库缺失。

这条规范不改变架构边界：图像 I/O 依赖应放在 `apps/renderd`、`apps/exportd` 或明确的平台适配器，不能把图像库头文件和实现塞进 `kernel/`；Qt、OpenGL、动态能力插件等已有禁令继续有效。

## 2. 选型门槛

引入一个库前，计划或证据记录必须写明：

1. 官方上游地址、版本或提交、下载校验方式和维护状态。
2. 目标平台和工具链支持情况（当前优先 macOS，后续保持 Windows/鸿蒙的适配边界）。
3. 直接许可证和传递依赖许可证，是否允许当前产品分发，以及需要随包携带的 NOTICE/许可证文本。
4. CMake/构建方式、ABI 和运行时插件路径；不能只在开发机上通过手工安装而无法复现。
5. 安全更新、输入损坏处理、最大尺寸/内存占用、性能和线程模型。
6. 与现有 `ResultCode`、`RgbaInput`、`ExportQueue` 和临时文件事务的映射方式。

至少比较两个候选，或在证据中说明为什么该能力只有一个可接受候选。不能以“最流行”“网上示例最多”作为唯一依据。

## 3. 获取、锁定和集成

- 依赖必须通过项目认可的可复现构建方式声明在 CMake 和依赖记录中，锁定版本/提交；禁止构建时无版本地从网络拉取 `latest`，禁止运行时下载和执行库。
- 优先使用官方源码、官方发布包或系统明确提供的受支持版本。下载的源码、补丁、许可证和校验信息必须可追溯；不能提交来源不明的二进制文件。
- 第三方库只由拥有该能力的模块链接。公共内核不因为调用方需要而直接链接图像库、网络库或推理运行时。
- 库不可用、版本不兼容或输入损坏时，返回明确的 `UnsupportedFormat`、`ImageCorrupt`、`IoFailed` 或相应结果码；不得回退到未经验证的手写实现。

## 4. 手写实现例外

只有在证据证明没有合适第三方库，或库的许可证/平台/性能/安全条件不能满足时，才允许手写通用算法。例外必须在计划和证据中记录检索过的候选、排除理由、范围、测试向量、模糊/损坏输入处理和后续替换路径。没有这条记录，手写实现按规范不通过。

## 5. 图像 I/O 的当前候选方向

这不是最终选型，只是下一阶段调查的起点：

- [OpenImageIO](https://openimageio.readthedocs.io/en/latest/oiiointro.html)（构建说明：[INSTALL](https://openimageio.readthedocs.io/en/stable/INSTALL.html)）：提供格式无关的 `ImageInput`/`ImageOutput`，官方安装文档说明其公共 API 使用 C++17、CMake，并支持 macOS/Windows；代码主要为 Apache 2.0，另有少量兼容 BSD 代码和第三方许可，需要逐项清点。
- [libvips](https://www.libvips.org/)：官方项目说明其低内存、按需处理和广泛格式支持，许可证为 LGPL-2.1-or-later；需评估其插件和传递依赖是否适合本项目分发。
- [LibRaw](https://www.libraw.org/docs)：官方文档定位为相机 RAW 读取库，提供 LGPL-2.1 或 CDDL 1.0 双许可证；其官方说明也提醒基础 RAW 转换不等同于生产级完整渲染，因此应把它与项目自己的 RAW/色彩管线边界分开评估。

候选库的事实以其官方文档和发布包为准；没有完成第 2 节选型记录前，不把任何一个候选写进生产 CMake。
