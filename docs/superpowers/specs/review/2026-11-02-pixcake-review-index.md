- [第三方依赖优先与引入规范](../2026-11-06-pixcake-third-party-dependency-policy.md)：通用能力优先复用成熟库，版本、许可证、平台和可复现构建必须有证据

两边冲突时沿用架构文首的裁决：用户能看见的行为以需求为准，代码放哪、谁可以 include 谁以架构为准。例外是标题上带 Free 的功能，以及架构第 17 节点名排除的能力：需求里即使写了操作步骤，本阶段也不实现，实现了同样不通过。

本套清单是第三份合同。它规定审核时怎么判「计划有没有做全」。它不新造滑杆、不新造点数、不新造快捷键。某条边界在上位文档里没写死时，会标明「本规范补齐」，改这条之前不许用相反的行为写代码。

所有新增第三方依赖和通用算法实现同时按《第三方依赖优先与引入规范》审核。清单没有写到的依赖问题，也不能以“能编译”或“测试通过”视为通过。

## 1. 审核什么时候做

用户说 review、审核、评审当前项目，或问「计划有没有实现全」，就按本目录七份清单逐条看代码、测试和最近一次测试输出。能编译、能打开窗口，不算通过。

还没写某个模块时，该模块相关行记「未实现」。不许删行，不许改成通过。

## 2. 七关，按这个顺序

| 顺序 | 清单 | 这一关在问什么 |
| --- | --- | --- |
| 1 | [业务契约](2026-11-02-pixcake-contract-checklist.md) | 接口、方法、参数、返回值、副作用是不是需求和要求的那一件事 |
| 2 | [边界条件](2026-11-02-pixcake-boundary-checklist.md) | 空、越界、除零、超时、并发、第三方异常、磁盘和损坏 |
| 3 | [安全 SafeList](2026-11-02-pixcake-safelist.md) | 注入、校验、密钥、日志、鉴权 |
| 4 | [性能](2026-11-02-pixcake-performance-checklist.md) | 能跑，但是放到本文件第 5 节的数据量上会不会又慢又漏 |
| 5 | [代码质量](2026-11-02-pixcake-quality-checklist.md) | 命名、单一职责、该有的注释、重复、过度设计 |
| 6 | [测试](2026-11-02-pixcake-test-checklist.md) | 单元、边界、异常、集成、回归有没有写、有没有跑过 |
| 7 | [可观测与回滚](2026-11-02-pixcake-ops-checklist.md) | 日志、指标、用户能看见的失败、回滚、回滚后数据还在不在 |

第 1 关有否决项没过，后面可以继续记问题，但结论已经是打回重写。不许用后几关的整理工作把结论改成通过。

## 3. 一行只有四种结论

| 结论 | 含义 |
| --- | --- |
| 通过 | 代码和测试对得上这一行，证据写到文件和测试名 |
| 不通过 | 做了，但和这一行相反、缺失或含糊 |
| 未实现 | 该做的模块还没有。整模块缺失时，这一行不是通过 |
| 不适用 | 架构第 17 节排除，或该模块这一轮明确不在审查范围。代码里要是出现了排除项，改判不通过 |

严重程度只有两类：

- **否决**：命中就打回重写。不接受在错误合同上打补丁。
- **必须补**：可以留在原来的模块结构上补齐。没补完之前，这一轮仍然不通过。

## 4. 打回重写是什么意思

否决项不是「记一笔以后再修」。实现建立在错误的参数、返回值、存储格式或依赖方向上时，整段按清单重写。

下面两例直接打回，不接受括号里的补丁：

- 用户文件里的色温存成 0 到 200，或曝光存成 0 到 10000。架构附录 B 要求存显示值。不接受「界面显示时再减 100」。（读写两边一起重写。）
- `kernel/` 的公开类型带上 Qt 控件或 `QOpenGL*`。不接受删掉几个暂时没用到的 include、把 Qt 类型留在头文件里。（按架构第 4、14 节重写这块的类型。）

审核时禁止为了让结论变绿而改需求、改架构或改本套清单去迁就代码。文档和代码冲突时，先写明冲突，这一轮结论是不通过。要改产品规则，先改上位文档，再重审。

## 5. 审核时用的数据量

这些数字用来拒绝「样例上能跑」的实现。除了需求里已经写明的上限，它们不是产品配额。

| 场景 | 审核时按这个量看 |
| --- | --- |
| 一次导入达到挑图询问 | 不少于 150 张，这是产品规则 |
| 一个项目里的照片 | 2000 张原图的元数据、筛选、排序、缩略图和导出队列 |
| 样片库 | 2000 张，单次导入 1000 张，这是产品规则 |
| 预设 | 数百条名称的列表和搜索 |
| 一次拖动滑杆 | 指针经过上百个中间值 |
| 创意批量 | 多张图，每张多个工具节点 |

2000 张照片的项目可以加载索引和缩略图。不可以一次把 2000 份参数正文或原图像素读进内存。

## 6. 开工前先写什么

本套清单就是编写实现之前要写清楚的规范。某个模块开始写代码之前，在当次审核记录里先列出它对应的契约编号、边界编号、安全编号、性能编号和测试编号。对不上号的行为，先补清单，再写代码。

架构第 17 节和第 3.1 节放弃的拆法，不因为「先做一个能跑的」而写进代码。

## 7. 审核记录

每次审核另写一份记录，不改清单正文。记录用下面的格式。

```text
标题：审核记录，日期，审查范围
结论：通过 / 打回重写
第 1 关到第 7 关：每关一个表，列是编号、结论、证据、差异
打回项：要重写的模块，禁止的补丁写法
未实现：哪些编号还没有代码
测试：命令，以及通过、失败或没跑
```

证据指到源文件、测试名，或「未实现」。没有证据的「通过」无效。

## 8. 本阶段不拿来判失败的东西

- AI 效果的像素不要求和官方模型逐点相同。入口、档位、禁用、生成张数、扣点和图层结果必须相同。
- `pixcake::gl::native` 可以有平台原生 OpenGL Core 函数体。审核看类型和方法是否与 Qt 后端逐字冻结、实现是否只留在 `gpu/backend/native`、公共 facade 和业务渲染是否没有 Qt/OpenGL 平台类型泄漏。
- 云协同、工作流编排、联机拍摄会话、芝士交付、ERP、手机和 iPad，只审需求第 2.1 节那一层入口在不在，以及有没有把深层协议写进内核。
- 本阶段不要求把告警发到手机或外部监控服务。用户能看见的失败原因，以及本机日志里数得出来的计数，仍然要有。
